# Requirements Analyzer (Аналізатор Вимог та Валідатор Якості)

Цей скіл виконує аналітичний аудит нормалізованих вимог із бази даних **«1. Нормалізовані вимоги»**, виявляє логічні прогалини, суперечності та неповноту, автоматично підтверджує якісні вимоги або формує реєстр проблем у розділі **«2. Проміжні результати аналізу вимог»** із відкритими питаннями та пропозиціями щодо вирішення.

Усі формулювання, запитання, таблиці та нотатки ведуться **виключно українською мовою**.

---

## ⛔ СУВОРЕ ОБМЕЖЕННЯ: Заборона самовільного прийняття рішень

> [!CAUTION]
> **Агент НЕ має права самостійно приймати рішення щодо бізнес-логіки!**
> 1. При виявленні прогалини або суперечності агент повинен:
>    - Чітко описати виявлену проблему.
>    - Сформулювати конкретні відкриті запитання до бізнес-аналітика (BA), продакт-овнера (PO) чи замовника.
>    - Запропонувати можливі варіанти вирішення (Варіант А, Варіант Б...), обґрунтувавши плюси та мінуси кожного.
> 2. **Агент НЕ обирає один із варіантів самостійно** і не фіксує його як остаточне правило до отримання явного рішення від людини/стейкхолдера.

## 🔍 Критерії Аудиту Якості Вимоги

Під час аналізу кожна нормалізована вимога оцінюється за 5 критеріями:

| Критерій | Що перевіряється | Приклад дефекту |
|---|---|---|
| **Повнота (Completeness)** | Чи визначені всі граничні значення, формати полів, обов'язковість та обробка помилок. | *Вказано «користувач вводить пароль», але не вказано обмеження довжини, спецсимволи чи регістр.* |
| **Однозначність (Unambiguity)** | Відсутність суб'єктивних слів: *«швидко»*, *«зручно»*, *«інтуїтивно»*, *«оптимально»*, *«приблизно»*. | *«Система повинна швидко завантажувати сторінку» (не вказано час у мілісекундах).* |
| **Несуперечливість (Consistency)** | Відсутність колізій між цією вимогою та іншими вимогами або архітектурою. | *В одній вимозі Email унікальний, в іншій дозволено мультиакаунт на одну пошту.* |
| **Тестованість (Testability)** | Чи можна побудувати однозначний тест-кейс із критерієм Pass/Fail. | *«Система підтримує високу стабільність» (немає SLO/SLA метрики для перевірки).* |
| **Обробка граничних випадків (Edge Cases)** | Поведінка при негативних сценаріях (дублікати, порожні значення, таймаут, відмова мережі). | *Описано тільки успішну оплату, відсутня поведінка при відхиленні транзакції банком.* |

## 🟢 Сценарій 1: Проблем НЕ виявлено (Вимога валідна)

Якщо вимога повністю задовольняє всі критерії якості:
1. Викликати інструмент `notion-update-page` для картки цієї вимоги в базі даних «1. Нормалізовані вимоги».
2. Оновити властивості:
   - **`Стан`**: `узгоджено`
   - **`Ким підтверджено`**: `AI Agent (Requirements Analyzer)`
3. Додати в коментар до картки або в історію аналізу коротку помітку:
   *«Вимога перевірена на повноту, однозначність та тестованість. Зауважень не виявлено.»*

---

## 🔴 Сценарій 2: Виявлено проблеми / прогалини / суперечності

Якщо вимога містить неточності, прогалини чи суб'єктивні формулювання:
1. **У базі даних «1. Нормалізовані вимоги»:**
   - Оновити стан вимоги на: **`в процесі аналізу`**.
   - Поле **`Ким підтверджено`** залишається **`null`** (порожнім).
   - У поле **`Нормалізація`** додати лаконічну помітку про дефект (наприклад: *«Потребує уточнення граничних значень довжини»*).

2. **У розділі «2. Проміжні результати аналізу вимог»:**
   - Сторінка: **`4018b55f-9a7e-81c8-ad3e-d8f74be12f55`** ([Відкрити сторінку](https://app.notion.com/p/4018b55f9a7e81c8ad3ed8f74be12f55)).
   - Додати або оновити таблицю проблемних вимог наступного формату:

### 📋 Структура таблиці проблемних вимог (Розділ 2)

| ID вимоги | Назва вимоги | Виявлена проблема / Дефект | Відкриті запитання (до BA / PO) | Пропозиції щодо вирішення (Варіанти) | Статус у блоці аналізу |

| **REQ-1** | [Реєстрація користувача](https://app.notion.com/...) | Відсутні вимоги до мінімальної та максимальної довжини поля «Ім'я» | 1. Яка мінімальна та максимальна довжина імені?<br>2. ## 🛠️ Порядок Виконання Аналізу через MCP

1. **Зчитування невирішених вимог:**
   - Викликати `notion-query-data-sources` для `collection://7882d176-0f8f-4c66-b396-604989a9ea81` із фільтром:
     `"Стан" != "узгоджено"`.
2. **Аналіз кожної знайденої картки:**
   - Зчитати властивості: `Назва`, `Нормалізована вимога`, `Тип`, `Джерело`.
   - Провести звірку за критеріями якості.
3. **Пакетне виконання дій:**
   - Для валідних вимог:
     ```json
     {
       "command": "update_properties",
       "page_id": "<page_id>",
       "properties": {
         "Стан": "узгоджено",
         "Ким підтверджено": "AI Agent (Requirements Analyzer)"
       }
     }
     ```
   - Для проблемних вимог:
     ```json
     {
       "command": "update_properties",
       "page_id": "<page_id>",
       "properties": {
         "Стан": "в процесі аналізу"
       }
     }
     ```
4. **Оновлення розділу 2 в Notion:**
   - Викликати `notion-update-page` для сторінки `4018b55f-9a7e-81c8-ad3e-d8f74be12f55` з `command: "insert_content"`, вставивши сформовану таблицю проблем, запитань та варіантів.
5. **Звіт у чат користувачеві:**
   - Скільки вимог підтверджено автоматично.
   - Скільки вимог переведено в статус «в процесі аналізу».
   - Перелік відкритих запитань з проханням до користувача затвердити один із запропонованих варіантів.
