# Knowledge Base Manager (Майстер-скіл наповнення Бази Знань проєкту)

Цей скіл є центральним диспетчером та координатором для наповнення, структурування та синхронізації бази знань проєкту в Notion на кореневій сторінці **[База знань проєкту](https://app.notion.com/p/4018b55f9a7e809a87c5e83a8185bd10)**.

Він оцінює вхідні матеріали з будь-яких джерел (документи, чат, Jira, Confluence, API), визначає цільовий розділ бази знань, делегує обробку відповідним субскілам та **забезпечує інтерактивну валідацію через уточнюючі запитання**, якщо даних недостатньо або є невизначеність.

> [!TIP]
> **🚀 Перший запуск проєкту:**
> Якщо структура бази знань у Notion ще не створена або запускається новий проєкт «з нуля», використовуйте скіл [`notion-project-init`](file:///.agents/skills/notion-project-init/SKILL.md). Він повністю автоматично створить кореневу сторінку, реєстр вимог (Notion Database) та всі 4 підпорядковані розділи.

Усі матеріали, описи та діалоги ведуться **українською мовою**.

## ❓ ПРАВИЛО ОБОВ'ЯЗКОВИХ УТОЧНЕНЬ (Ask Clarifications Rule)

> [!IMPORTANT]
> **Ніколи не робити здогадок замість користувача!**
> Агент зобов'язаний зупинитися і поставити уточнююче запитання (через `ask_question` або пряме звернення), якщо:
> 1. **Недостатньо контексту:** у наданому джерелі відсутні критичні параметри (наприклад: не вказано граничні значення, обов'язковість поля, очікувані статус-коди HTTP).
> 2. **Конфлікт або суперечність:** різні розділи вихідного документа, тікети Jira або повідомлення в чаті суперечать одне одному.
> 3. **Неоднозначна ціль наповнення:** незрозуміло, в який саме розділ бази знань користувач хоче занести інформацію (наприклад: це вже фінальне затверджене рішення для розділу 3 чи тільки чернетка аналізу для розділу 2?).
> 4. **Неповнота бізнес-логіки:** вказано позитивний сценарій (Happy Path), але відсутні правила обробки помилок (Edge Cases / Negative Scenarios).

### Шаблон уточнюючого запитання:
* **Що саме виявлено:** (наприклад: *«У вимозі щодо відновлення пароля не зазначено термін дії тимчасового токена безпеки»*).
* **На що це впливає:** (наприклад: *«Це унеможливлює точну нормалізацію вимоги та побудову негативного тест-кейсу на експірацію токена»*).
* **Варіанти вибору / Пропозиції:**
  - Опція 1: Зафіксувати у розділі «2. Проміжні результати аналізу» як відкрите питання до стейкхолдерів.
  - Опція 2: Зафіксувати як вимогу зі станом `потребує аналізу` та вказати зауваження в полі «Нормалізація».
  - Опція 3: Вказати точне значення прямо зараз у чаті.

## 🔄 Покроковий Процес Роботи Майстер-Скіла

### Крок 1. Аналіз вхідного артефакту
1. Зчитати та ідентифікувати формат вхідних даних:
   - Документ Word (`.docx`), Markdown (`.md`), Google Doc, таблиця Excel/GSheets.
   - Експорт або тікет із Jira (`jira-ithillel`).
   - Експорт або сторінка з Confluence.
   - Текст/нотатки користувача в поточному чаті.
2. Провести первинну оцінку: чи містить текст вимоги, аналітику, рішення, задачі чи схему API?

### Крок 2. Перевірка на повноту та валідація сумнівів
1. Якщо виявлено білі плями, суперечності чи пропущені умови:
   - Сформулювати лаконічні та чіткі питання користувачеві.
   - Отримати відповідь перед внесенням змін у базу знань.

### Крок 3. Маршрутизація та делегування субскілам

#### 🔹 1. Якщо це вимоги -> Делегувати скілу `requirements-normalizer`:
- Застосувати **Золоте правило незмінності суті**: розбити на атомарні твердження без додумувань.
- Класифікувати тип: *Функціональна, Нефункціональна, Бізнес-вимога, Технічна, Інтеграційна*.
- Зберегти у базу даних `1. Нормалізовані вимоги` (`collection://7882d176-0f8f-4c66-b396-604989a9ea81`) зі станом **`потребує аналізу`** та порожнім полем **`Ким підтверджено: null`**.
- **Поле «Ким підтверджено» заповнюється виключно після переведення вимоги в стан `узгоджено`** (вказується особа/стейкхолдер, який підтвердив вимогу).

#### 🔹 2. Якщо це аналіз вимог та виявлення проблем -> Делегувати скілам [`requirements-analyzer`](file:///.agents/skills/requirements-analyzer/SKILL.md), [`requirements-resolver`](file:///.agents/skills/requirements-resolver/SKILL.md) та [`requirements-decision-applier`](file:///.agents/skills/requirements-decision-applier/SKILL.md):
- **requirements-analyzer**: Здійснює аудит нормалізованих вимог зі станом, відмінним від `узгоджено`.
  - Якщо проблем немає: переводить у стан `узгоджено` та вказує у полі `Ким підтверджено`: `AI Agent (Requirements Analyzer)`.
  - Якщо виявлено дефект/прогалину: переводить стан у `в процесі аналізу`, додає запис у таблицю проблемних вимог на сторінці `2. Проміжні результати аналізу вимог` (`4018b55f-9a7e-81c8-ad3e-d8f74be12f55`). Агент сам рішення не приймає.
- **requirements-resolver**: Формує локальну анкету узгодження `.md` у папці `clarifications/` (поза контролем Git) із чіткими полями для відповіді людини.
- **requirements-decision-applier**: Аналізує заповнені людиною анкети у `clarifications/*.md`. Якщо рішення усуває проблему — переводить стан вимоги в базі на `узгоджено`, вписує в `Ким підтверджено` агента `AI Agent (Requirements Decision Applier)`, оновлює текст нормалізованої вимоги, а на сторінці Розділу 2 додає біля вимоги позначку `✅ Вирішено`.

#### 🔹 3. Якщо це архітектурне/тестове рішення -> Оновити сторінку `3. Зафіксовані прийняті рішення`:
- ID сторінки: `4018b55f-9a7e-811a-960e-caf7e93058a2`.
- Фіксується автоматично через скіл `requirements-resolver` (при узгодженні проблемних вимог) або вручну за форматом ADR (Architecture Decision Record):
  ```markdown
  ### ⚖️ ADR-[Номер]: [Коротка назва рішення]
  - **Статус:** Затверджено / На обговоренні
  - **Контекст:** Чому виникла необхідність прийняття рішення.
  - **Прийняте рішення:** Конкретний обраний підхід (стек, критерії, правила валідації).
  - **Наслідки:** Вплив на тести, розробку та інфраструктуру.
  ```

#### 🔹 4. Якщо це задачі на тестування -> Оновити сторінку `4. Сформовані задачі`:
- ID сторінки: `4018b55f-9a7e-812b-a86d-eac930204284`.
- Структура запису:
  ```markdown
  ### 🎯 План задач: [Спринт / Епік / Модуль]
  - [ ] **TASK-[№]:** Написання E2E тестів для форми реєстрації (Cypress/Playwright)
  - [ ] **TASK-[№]:** Автоматизація валідації статус-кодів API
  - **Критерії готовності (DoD):** Покриття тест-кейсами, 100% проходження в CI.
  ```

#### 🔹 5. Якщо це специфікація API -> Делегувати скілу [`openapi-spec-generator`](file:///.agents/skills/openapi-spec-generator/SKILL.md):
- ID сторінки в Notion: `4018b55f-9a7e-8182-bcf2-f14567c2c329` ([5. Схема АПІ](https://app.notion.com/p/4018b55f9a7e8182bcf2f14567c2c329)).
- Обробляє Swagger UI, Swagger/OpenAPI JSON/YAML схеми, описи або код контролерів.
- Генерує стандартизовану специфікацію OpenAPI 3.0+ з матрицею ендпоінтів, моделями DTO, статус-кодами (2xx, 4xx, 5xx) та машиночитабельним блоком специфікації.
- Оновлює сторінку за допомогою `notion-update-page` (`command: "insert_content"`).

## 📊 Крок 4. Звітність користувачеві

Після кожного циклу наповнення бази знань майстер-скіл надає користувачеві вичерпне резюме:
1. **Які джерела було опрацьовано** (з посиланням на файли/тікети/повідомлення).
2. **Які розділи бази знань було наповнено** (з прямими клікабельними лінками на картки/сторінки в Notion).
3. **Які питання чи прогалини було виявлено** та який поточний статус їх вирішення.
4. **Рекомендовані наступні кроки** для команди тестування та розробки.
