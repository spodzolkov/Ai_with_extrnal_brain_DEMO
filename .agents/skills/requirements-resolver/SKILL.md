# Requirements Resolver (Вирішення Проблемних Вимог через Опитувальні Анкети)

Цей скіл організовує інтерактивний цикл усунення дефектів і прогалин у вимогах:
1. Витягує проблемні вимоги з Notion (із бази **«1. Нормалізовані вимоги»** або сторінки **«2. Проміжні результати аналізу вимог»**).
2. Генерує структурований Markdown-файл (`.md`) у локальній папці `clarifications/` (яка виключена з Git через `.gitignore`) із **чіткими полями для введення відповідей людиною**.
3. Після заповнення анкет людиною (стейкхолдером / BA / PO) скіл зчитує надані відповіді, оновлює вимоги до стану **`узгоджено`**, заповнює колонку **`Ким підтверджено`**, фіксує рішення в **розділі 3 (ADR)** та маркує проблеми як вирішені в **розділі 2** Notion.

Усі матеріали, запитання, форми та коментарі ведуться **виключно українською мовою**.

---

## 🔒 Захист від Git (Zero Leakage)

> [!IMPORTANT]
> Усі файли опитувань та чернетки відповідей зберігаються виключно в директорії:
> **`clarifications/`** (відносно кореня проєкту).
>
> Ця директорія внесена до `.gitignore` і **ні за яких обставин не потрапляє під контроль версій Git**.

```mermaid

        CheckStatus -- "Статус: 'взята в роботу' АБО 'вирішена'" --> Skip[⛔ Пропуск:\nНЕ потрапляє в файл аналізу]
        CheckStatus -- "Відкрита / Потребує вирішення" --> Generator[Генерація анкети .md]

    end

    subgraph Phase2 [Фаза 2: Рішення людини]
```

## 📝 Етап 1: Генерація анкети проблемних вимог

1. Скіл знаходить проблемні вимоги в Notion (у розділі «2. Проміжні результати аналізу вимог» або зі станом `в процесі аналізу` в базі вимог).
2. **Обов'язкова перевірка статусів перед додаванням у файл:**
   > [!IMPORTANT]
   > ### 🚫 Правило фільтрації (виключення з файлу аналізу):
   > **Якщо в блоці аналізу вимог (Розділ 2 Notion) вимога має статус:**
   > - **`взята в роботу`** (вимога вже перебуває в опрацюванні іншим аналітиком / стейкхолдером)
   > - **`вирішена`** (або має позначку `✅ Вирішено`)
   > 
   > ❌ **Така вимога НЕ потрапляє у файл аналізу (`clarifications/*.md`)!**
   >
   > У файл аналізу додаються **виключно активні та відкриті проблемні вимоги**, які ще не взяті в роботу і не мають прийнятого рішення.

3. Створює файл із часовою міткою: `clarifications/clarification_YYYYMMDD_HHMM.md`.
4. Для кожної відібраної проблемної вимоги генерує уніфікований блок із чітко виділеними секціями для вводу.

### 📋 Еталонний шаблон анкети (.md)

```markdown
# 📋 Анкета узгодження проблемних вимог (Дата: ДД.ММ.РРРР)

> **Інструкція для стейкхолдера / BA / PO:**
> Будь ласка, заповніть виділені блоки `[ ]` та поля `ВІДПОВІДЬ СТЕЙКХОЛДЕРА` для кожної вимоги.
> Після завершення збережіть файл — агент автоматично застосує ваші рішення до бази знань.

---

### 🔴 Проблема №1: [REQ-1] Реєстрація нового користувача
- **Посилання в Notion:** [Відкрити картку REQ-1](https://app.notion.com/...)
- **Поточний текст вимоги:**
  > Користувач вводить ім'я, прізвище, email та пароль для створення облікового запису.
- **Виявлена проблема / дефект:**
  Відсутні граничні значення для довжини пароля та обов'язкові вимоги до спецсимволів.
- **Відкриті запитання:**
  1. Яка мінімальна та максимальна довжина пароля?
  2. Чи обов'язкові цифри, великі літери та спецсимволи?
- **Запропоновані варіанти вирішення:**
  - [ ] **Варіант А:** Довжина 8..64 символи, мінімум одна велика літера, одна цифра та один спецсимвол.
  - [ ] **Варіант Б:** Довжина 6..30 символів без вимог до спецсимволів (спрощений UX).
  - [ ] **Варіант В:** Інший варіант (опишіть нижче).

#### ✍️ ПОЛЯ ДЛЯ ВІДПОВІДІ (ЗАПОВНЮЄ ЛЮДИНА):
- [ ] **Обраний варіант:** Варіант А
- **Рішення / Точні вимоги:** 
  > [Введіть фінальне формулювання правила або уточніть обраний варіант тут]
- **Ким підтверджено (ПІБ та роль):** 
  > [Наприклад: Олена Коваль (Lead BA)]
- **Дата підтвердження:** 
  > [РРРР-ММ-ДД]
- **Статус затвердження:** 
  > [ узгоджено | відхилено ]

---
```

## 📥 Етап 2: Заповнення стейкхолдером

- Людина відкриває файл у будь-якому редакторі (VS Code, Typora, Notepad тощо).
- Заповнює текстові поля в цитатах `> [ ... ]`.
- Зберігає файл.

---

## ⚡ Етап 3: Автоматичне застосування рішень (Sync to Notion)

Коли користувач повідомляє про готовність анкети або передає шлях до файлу (наприклад: *«Я заповнив анкету clarifications/clarification_20261022.md, застосуй рішення»*):

1. **Зчитування та валідація:**
   - Зчитати вказаний `.md` файл.
   - Перевірити наявність обов'язкових полів:
     * `Рішення / Точні вимоги` (не пусте).
     * `Ким підтверджено` (не пусте).
     * `Статус затвердження` (`узгоджено` або `відхилено`).
   - Якщо хоча б одне поле для певної вимоги не заповнене — зупинитися і повідомити користувача, які саме поля залишились порожніми.

2. **Оновлення в базі даних «1. Нормалізовані вимоги»:**
   - Знайти картку за `ID вимоги` (наприклад, `REQ-1`) у `collection://7882d176-0f8f-4c66-b396-604989a9ea81`.
   - Викликати `notion-update-page`:
     * **`Стан`**: значення з анкети (`узгоджено` або `відхилено`).
     * **`Ким підтверджено`**: ПІБ та роль людини з анкети.
     * **`Нормалізована вимога`**: оновлений атомарний текст із врахуванням прийнятого рішення.
     * **`Нормалізація`**: помітка про внесені уточнення (наприклад: *«Уточнено граничні значення пароля згідно з рішенням Олени Коваль від 22.10.2026»*).

3. **Фіксація в розділі «3. Зафіксовані прийняті рішення» (`4018b55f-9a7e-811a-960e-caf7e93058a2`):**
   - Додати запис у форматі ADR:
     ```markdown
     ### ⚖️ ADR: Узгодження вимоги [ID вимоги] ([Назва])
     - **Статус:** Затверджено
     - **Ким підтверджено:** [ПІБ та роль] (Дата: [Дата])
     - **Контекст проблеми:** [Опис дефекту / суперечності]
     - **Прийняте рішення:** [Текст остаточного рішення]
     ```

4. **Оновлення в розділі «2. Проміжні результати аналізу вимог» (`4018b55f-9a7e-81c8-ad3e-d8f74be12f55`):**
   - Оновити рядок у таблиці проблем: додати позначку `✅ Узгоджено ([ПІБ], [Дата])` або видалити вирішений пункт із реєстру активних проблем.

5. **Фінальний звіт:**
   - Надати користувачеві стислий підсумок про те, скільки вимог успішно узгоджено, хто їх підтвердив і які записи в Notion оновлено.
